---
name: compute-resource-setup
description: Connect a user's SSH/Slurm computing resource, inspect software and queues, save a reusable profile, and run explicitly requested Quantum ESPRESSO calculations.
---

Use the existing Harness tools, structured user questions, task records and project artifacts. Keep connection, scheduler and scientific-program configuration separate. Do not hard-code provider accounts, hosts, queues, paths or software modules.

## Connect and configure

1. Use `highzyme_compute_resources` to check existing profiles. Reuse an existing SSH alias when available. Otherwise collect host, port and username. Ask for a local private-key **path** or let the user select it in Settings; never request, read or include private-key contents in messages, project files or tool arguments.
2. Call `highzyme_compute_setup` with `action: inspect` and the connection fields. This reads environment information without installing packages or submitting a job. Explain an authentication/host-trust failure concretely and ask only for information needed to resolve it. Existing OpenSSH config, agent and known-host checks are reused.
3. Inspect the returned writable directory, Slurm queues/account associations, QE executable and `qe_modules`. If the program is not on PATH, use an explicit module from the detected list. If several appropriate choices remain, ask the user. A typical user-approved `setup_script` is `module purge\nmodule load <selected-module>`. Check it again. Do not edit shared software or system settings.
4. Set reusable `defaults` for `ranks` (MPI processes), `threads` (per process), `memory_mb` (total Slurm job memory) and `timeout_seconds`, and optional `limits` with the same keys. Preserve an existing profile's fields when updating it. Ask about allocation limits when they are unknown; do not claim detected queue names establish a CPU or time allocation. Save the profile using `action: save`. Enable it only when requested with `action: enable`; compute submissions also require the execution-permission switch in Settings. Keep credentials/configuration in the local application state, outside project artifacts and Git.

The setup assistant uses an ordinary conversation and does not require a research project. Its resource profile remains application-level. Actual calculations require an open project or case. Report connection, Slurm submission readiness, QE availability and the last completed calculation separately. `ready: true` means submission is available; check `capabilities` for the requested program. Configuration alone never establishes scientific convergence. After saving, direct the user to Settings > Tools & compute resources > Compute resources to review or enable it.

For a new host that is not yet trusted, help the user verify its SSH fingerprint with their provider and establish trust through their SSH client. Do not disable host verification. For an encrypted key, let the user's SSH agent handle unlocking rather than collecting its passphrase in conversation.

## Submit and retrieve

- Generic authorized code uses `highzyme_compute_submit` with project input files and explicit ranks, threads, memory and walltime. Use the returned job ID with status/cancel; never retry an ambiguous submission automatically. The application polls status without needing repeated model calls.
- For Quantum ESPRESSO call `highzyme_qe_prepare` first: select an explicit periodic structure and UPFs from project files, SCF, fixed-cell or variable-cell relaxation, cutoffs in Ry and a three-integer k-point grid. For convergence, energy comparisons, DOS/PDOS/bands, density/Bader, thermochemistry or NEB, load `scientific-computing` and use `highzyme_qe_workflow_prepare`. Check its required programs; executable overrides can be saved in `program_commands`. QE workflows do not require Python on compute nodes. Missing job specifications use the selected resource's defaults; overrides must respect its limits. Reuse the existing structure reader. Ask for missing scientific settings that affect the calculation; do not invent a structure, pseudopotential identity, magnetic state or convergence claim.
- Show the prepared structure, pseudopotentials, effective parameters, resource name and requested job specifications before submission. The project task panel also shows the prepared input and a Submit calculation button. Call `highzyme_qe_submit` with the prepared `job_id` only after authorization for this calculation; an existing request to run that calculation is sufficient, without a second approval for the same scope. Preparation is local and requires no enabled compute allocation. Changed inputs must be prepared again so the saved request describes the actual submitted files. Repeated submission of the same job returns its existing record.
- After the job ends, use `highzyme_qe_collect`. It retrieves selected outputs, checks electronic/geometry convergence, reads the structure through ASE and publishes the report, parameters, inputs, logs and structures as one project artifact with Git history.
- Submit a minimal smoke test only when the user asks for it, using `highzyme_qe_test`. It prepares the bundled two-atom Si SCF, downloads its official UPF with a source hash, and requests one core, 1024 MiB and at most five minutes. Use its returned job ID rather than calling the test tool again. The example is also available under `examples/general-research/qe-smoke`. This checks the execution and result-import chain, not material performance or production convergence.

Report concrete states: connected, submission ready, software available, prepared, queued/running, calculation converged or failed, and result imported. A cancelled preparation is not a remotely cancelled job; cancelling a submitted task uses the scheduler, while stopping a chat does not cancel that task. Retrieval retries use the original job ID and never repeat computation. If configuration requires substantial independent diagnosis, reuse a native Harness subagent with a bounded task and the same permissions; routine onboarding stays in the current conversation.
